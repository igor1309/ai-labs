Two narrowings are flagged as warnings.

### Finding 1 — STU-07 "distinguish confusing concepts" is narrowed away by the accepted-corpus ADR (warning)

- **Verdict:** warning (loss)
- **What:** INT-02 and STU-07 commit Agonara to exposing *confusing/easily-confused neighbor concepts with the distinction to preserve*. ADR-010 enumerates the accepted-corpus content types it owns and omits the confusable-neighbor relationship, silently narrowing the concept model to topics/concepts/definitions/principles.
- **Why:** Loss rule — an ADR that fixes the accepted-corpus content set (a closed list with MUST) without carrying an intent commitment narrows that commitment without acknowledging it. The reader of ADR-010 cannot tell that "confusing neighbors" is a required concept relationship.
- **Side A:** `intent_learning_program_app.md:116` (INT-02 acceptance signal) — "A student can inspect a topic and see its key concepts, definitions, principles, and **confusing neighbors**." Reinforced by STU-07 `student_user_stories.md:74-80` "distinguish concepts that are easy to confuse … confusing or related concepts can be shown together with the distinction to preserve."
- **Side B:** `adr-010-...:48` (ADR-010 Decision) — "Corpus Storage MUST own accepted corpus records for a `Program`, including accepted topics, concepts, definitions, principles, material references, source metadata used by accepted content, accepted assessment items, and accepted assessment criteria." No confusable-neighbor / concept-distinction relationship appears here or in the Rules/Invariants list (`adr-010-...:66-88`).
- **Suggested fix:** advisory, point to the ADR. Add confusable-neighbor / concept-distinction relationships to ADR-010's owned-content enumeration (or add one explicit Non-Goal line deferring it, e.g. "concept-relationship/confusable-neighbor modeling is deferred to a later corpus-schema slice"). Either acknowledges the commitment instead of dropping it silently. ADR-010 line 109 already defers "exact accepted corpus schema," but that defers *schema shape*, not the *existence* of the relationship class — so the commitment is currently invisible.

### Finding 2 — CUR-13 / suggestion-origin traceability is not carried by any curation-boundary ADR (warning)

- **Verdict:** warning (loss)
- **What:** CUR-13 commits Agonara to exposing *why* an LLM/draft suggestion was proposed (source, prompt context, supporting evidence) **before acceptance**, so the curator can judge it. ADR-010 carries provenance only for **accepted** corpus (acceptance "MUST preserve provenance to the … LLM suggestion … that justified the change"), but no ADR carries the pre-acceptance, draft-side suggestion-origin visibility that CUR-13 requires.
- **Why:** Loss rule — CUR-13's commitment is about Curator Workspace draft state (suggestion origin visible *before* the accept/reject decision). ADR-010 assigns Curator Workspace ownership of "LLM-assisted suggestions, gap analysis, and curator review state" but does not carry the requirement that origin/evidence be inspectable on the draft. The commitment is neither realized nor deferred.
- **Side A:** `curator_user_stories.md:123-129` (CUR-13) — "I want to see why a suggestion was proposed so that I can judge whether it belongs in the program corpus. … a suggestion exposes its source, prompt context, or supporting evidence **before acceptance**."
- **Side B:** `adr-010-...:80` (ADR-010 Rules) — "Acceptance MUST preserve provenance to the accepted source, candidate, draft, LLM suggestion, or curator rationale that justified the change." This is acceptance-time provenance only; `adr-010-...:52,76` list draft ownership ("LLM-assisted suggestions … review state") without a pre-acceptance origin-visibility commitment.
- **Suggested fix:** advisory, point to the ADR. This is genuinely an open question rather than a hard contradiction — ADR-010 explicitly leaves Curator Workspace draft *behavior* (UI, suggestion workflow) to later specs (`adr-010-...:115` "Curator Workspace UI", ADR-009 `adr-009-...:104` "Curator Workspace draft and suggestion workflow"). If suggestion-origin visibility is intended to be a draft-workflow spec concern, the ADRs are clean and this should be tracked as an open question (below). If it is an ownership commitment, add a one-line ADR-010 invariant that Curator Workspace draft suggestions retain inspectable origin/evidence. Flagged as a warning because the commitment currently has no carrier and no explicit deferral.

## Coverage findings

One intent capability is carried by no ADR and is not explicitly deferred.

### Finding 3 — CUR-09 coverage-gap discovery is uncovered and not deferred (warning)

- **Verdict:** warning (coverage)
- **What:** CUR-09 (and the product-intent capability "находить пробелы в покрытии") commits Agonara to letting a curator *see gaps in topics, concepts, materials, or checks*. ADR-010 names "gap analysis" only as a thing Curator Workspace *owns as draft state*, but no ADR carries gap-discovery as a capability, and no ADR or intent line explicitly defers it (e.g. "out of first slice").
- **Why:** Vertical-coverage rule — every intent capability must be reflected in at least one ADR or explicitly deferred. Gap discovery appears only incidentally in an ownership enumeration, not as a carried capability, and nothing marks it deferred.
- **Side A:** `curator_user_stories.md:89-95` (CUR-09) — "I want to see gaps in topics, concepts, materials, or checks so that the program can be improved deliberately." Echoed in `intent_learning_program_app.md:152` "LLM может помогать … находить пробелы в покрытии."
- **Side B:** `adr-010-...:52` — "Curator Workspace MUST own research intake, candidate topics, … LLM-assisted suggestions, **gap analysis**, and curator review state before acceptance." This assigns ownership of gap-analysis *state* but no ADR decides gap *discovery* behavior, and no Non-Goal line defers it.
- **Suggested fix:** advisory. Either (a) acknowledge in ADR-010 (or a future Curator Workspace ADR) that gap discovery is a Curator Workspace capability deferred to a later curation-workflow slice — a one-line Non-Goal addition makes the deferral explicit and closes this finding — or (b) accept it as a planned-but-unsequenced capability tracked at intent→spec. Low severity: ownership is already placed in Curator Workspace; only the explicit "carried or deferred" marker is missing.
