Agonara

A structured learning program environment built around curated programs, progression, and evidence of mastery.

From the ancient Greek agon — exercise, trial, disciplined striving. Three roles share one program: the student who learns by evidence, the program curator who shapes the corpus, and the admin who keeps the instance operable.

Boundaries

  • Student stories describe personal learning, assessment, feedback, and progress.
  • They do not define how the corpus is created, curated, or approved.
  • They do not define membership policy, invitation policy, or recovery.
  • Program corpus and student state remain separate. Membership and learning state remain separate.

Program Curator

Creation, refinement, and acceptance of program content. Curators own the corpus; LLM output is draft until explicitly accepted.

Program Curation

CUR-01

Create program from grounded sources

Public plans, exam requirements, standards, materials, research.

A curator can attach the source set used to justify initial structure.
CUR-02

Add topics and concepts

Make learning scope explicit.

Accepted topics and concepts appear separately from unaccepted drafts.
CUR-03

Link materials to topics and concepts

Each accepted material shows the topic or concept it supports.
CUR-04

Add checks and assessment items

Understanding can be verified.

A topic can include accepted checks students can use to verify understanding.
CUR-05

Define assessment criteria

Evaluation tied to the program, not improvised per attempt.

A check or prompt references accepted criteria owned by the corpus.
CUR-06

Keep accepted content separate from drafts

Corpus remains controlled.

Draft suggestions never appear as accepted corpus until explicit acceptance.

CUR-10

Boundaries

Admin

15 stories · v0.2.1

Operational control of a private Agonara instance — identity, credentials, Admin authority, audit, and exceptional recovery. Admin authority does not replace Program Curator ownership of content.

Instance Setup

ADM-01

Initialize private instance

Start the instance with a first admin identity.

A new instance cannot become operational without at least one active Admin.

Identity Administration

ADM-02

Create internal identity

A stable subject for ownership and action.

The Identity exists independently of any credential or product role.
ADM-03

Bind credential to identity

Authenticate without making the credential the source of ownership.

Authentication resolves to the intended Identity while role grants stay separate.
ADM-04

Disable identity

Stop access without deleting historical ownership and audit references.

A disabled Identity cannot initiate new actions; historical references remain readable.
ADM-05

Inspect identities and credential bindings

Diagnose access and recovery state.

Admin can inspect active and disabled identities with credential-binding state.

Access Administration

ADM-06

Inspect program participation authority

Diagnose access without becoming the normal membership operator.

Inspection shows the membership grant and scope without creating or changing it.
ADM-07

Trace participation authority changes

Diagnose access loss or restoration.

Trace output points to membership or recovery records without recreating revoked access.
ADM-08

Assign or revoke admin role

Transfer operational control without changing learning-domain ownership.

Admin changes affect only instance-level operations.
ADM-09

Prevent last-admin removal

The instance cannot lose operational control.

Removing the last active Admin is rejected.

Audit and Recovery

ADM-10

Audit identity and access operations

Sensitive access changes must be attributable.

Each sensitive operation records the acting and affected identities and the change.
ADM-11

Include identity state in backup and restore

Recovered instances preserve access and ownership context.

Backup/restore covers identities, credential bindings, Admin authority, and recovery state.

Membership Recovery and Audit

ADM-12

View program membership state

Diagnose access and participation issues.

Admin can inspect membership state without becoming the normal operator.
ADM-13

Recover broken membership access

A valid student or curator can regain access during operational recovery.

Exceptional recovery restores valid access while preserving attribution.
ADM-14

Revoke operationally invalid membership

Recover the instance from incorrect or unsafe access state.

Exceptional revocation changes membership without making Admin the normal manager.
ADM-15

Audit membership changes

Participation changes can be diagnosed and audited.

Records include acting identity, affected identity, program, participation kind, and result.

Boundaries

  • Admin stories describe operational control of a private Agonara instance.
  • They do not describe student learning flow, curator content acceptance, corpus editing, or learning-domain authority.
  • Admin authority does not replace Program Curator ownership of accepted content.
  • Admin membership operations are exceptional recovery and audit, not the normal product flow.
