Two layers

<repo>/.agister over ~/.agister

Every document below can live in the repo's .agister or in home, in the same layout.

  • A repo document replaces home's of the same kind and name, whole. Fields are never merged.
  • What exists is the union of both layers.
  • Documents name each other by name, not by path. So a process in home can name verify:repo or a prompt, and each repo supplies its own.
  • Home is $AGISTER_HOME, else ~/.agister. Agents cannot reach home; they can change a repo's .agister when they may write the repo.

Workflow

workflows/<name>.yaml · run with agister run <name>

Composes process calls into one run. Its settings fix what each call receives, never whoever starts it.

Holds

input.params
what the caller supplies, each with an optional default
input.values
resolved once from the params, before any node starts; every fan-out node receives the same ones

Names

fan_out[].uses
a process per node, all run at once over the same inputs
join.uses
one process, given the fan-out nodes' results

Fan-out then join is the only shape today: no conditions, loops or graphs. The other workflow here is adr_review: one ADR review, then the judge.

Process

processes/<name>.yaml · run with agister run <name>

A named agent call: the task, what it takes in, and what must come out.

Holds

input.instruction
the task, in words
input.params
what the caller supplies
input.values
the inputs, each from a source: param, file, git.revision, git.merge_base, git.diff, git.changed_files, prompt
workspace.checkout
the value whose revision the call works in
workspace.setup
its own command to prepare that checkout
tools.require
permissions the call cannot do without
timeout, retry, …
limit overrides; they may only narrow its policy

Names

uses
its agent
policy
its policy
output.schema
its output schema
verify
its verification, by name or held inline
input.values[].name
a prompt, where the source is prompt
skills
its skills

A process with a verification, like this one, is still a process, not a workflow.

Output schema

schemas/<name>.json

A JSON Schema the process's output must match.

A process names it as output.schema. Only JSON is supported.

Verification

verifies/<name>.yaml, or inline in the process

A command that must pass on the call's changes before the call completes.

Holds

command
what to run
timeout
how long it may take
max_attempts
how many turns the agent gets to make it pass
instruction
what the agent is told when it fails

A process in home can name verify:repo, and each repo supplies its own verifies/repo.yaml.

Prompts

prompts/<name>.md

Plain text: the file is the value. A process takes one as an input, and may mark it optional; a missing optional prompt is left out.

Here: prompts/go-testing-seams.md and prompts/go-architecture.md.

Skills

skills/<name>/SKILL.md

One SKILL.md each, the folder's only file. A process names its skills and an agent names its own; the two lists are separate.

Names

skills (in a process)
the skills this call needs for its task
skills (in an agent)
the skills this agent always carries

Policy

policies/<name>.yaml

Execution defaults for the processes that name it. It speaks in permissions, never in a runtime's tools.

Holds

workspace.access
read-only or read-write
workspace.scope
candidate or repository
tools.allow, tools.deny
permissions, from the service's vocabulary; denied wins over allowed
timeout
within the service's maximum
retry.max_attempts
within the service's maximum
max_cost_usd
within the service's maximum, if it sets one
stale
when a silent or looping call is ended

Agent

agents/<name>.toml

A runtime profile: who does the work and how hard. It carries no task and no permissions.

Holds

model, model_family
which model
effort
one of the efforts its runtime mapping accepts
session
fresh-only or resumable

Names

runtime
its runtime mapping
skills
its own skills

Runtime mapping

runtimes/<name>.yaml

One adapter, described in permissions: what each of its tools or sandbox modes lets an agent do.

Holds

adapter
claude-code, codex, pi or opencode
efforts
the efforts it accepts
primitives.select
one (sandbox modes) or any (tools)
primitives.items[].grants
the permissions that primitive grants, from the service's vocabulary
primitives.items[].verified
the runtime versions it was observed on

Service

service.toml · one, with no name

Applies to every run. No document names it; policies and runtime mappings must keep its rules.

Holds

max_timeout
the longest any call may run
max_attempts
the most attempts any call may have
max_verify_attempts
the most turns a verification may allow
max_cost_usd
the most any call may cost, if set
permissions
the vocabulary: a policy uses only these, a runtime mapping grants only these
writing
the permissions that change the workspace; read-only access withholds them
state_reaching
permissions that would reach Agister's own state; never granted

Workspace

workspace.yaml · one

The default checkout setup, for processes that check out a revision and declare none of their own.

Holds

setup.command
what prepares a fresh checkout
setup.timeout
how long it may take

Blocks

blocks.yaml · one, repo only

What this repo refuses, even though home allows it.

Holds

blocks[].ref
agent:<name>, process:<name>, workflow:<name> or runtime:<name>
blocks[].reason
why, optional

How they compose

Limits only narrow

  • The service bounds the policy, the policy bounds the process, the process bounds the caller.
  • Asking for more than the level above allows is rejected, never quietly reduced.
  • A denied permission always wins over an allowed one.

Where permissions meet primitives

  • The call's effective permissions meet its agent's runtime mapping.
  • A primitive is granted only if everything it grants is allowed.
  • An allowed permission that no primitive provides is withheld. If the process requires it, the call is refused.
