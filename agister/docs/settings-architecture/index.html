Agister · Settings

Agister's settings architecture

Agister's settings are documents that name each other by name. In agister run <workflow> the name picks one workflow; nothing else is run. Each of its nodes uses a process and binds an agent to it. A process names its output schema, verification, prompts and skills, and may extend a base process; a file input may name the brief forms its text must have. An agent names its runtime mapping and its own skills. The service is never picked: it has no name, and it applies to every run.

The diagram reads top down, in the order agister run resolves the settings: the command picks the workflow it sits on. Beside each box's name are a few of the document's own fields; the sections below give them all. A box inside another is part of it or bound by it, and boxes side by side inside one box are on one level: a node's process and agent. A node is drawn once, stacked for the many a workflow may have. The rows in a process or an agent are the documents it names; the process's base is one of them, marked extends. The service is no box in the flow but the frame around it. Documents compose by field across home, the repository's .agister and the nearest project's .agister below the worktree root. The launch directory or --dir selects the project. Nested maps merge by key; scalars and lists replace whole ([] means none). A partial sets only what it changes; prompts, skills and schemas are taken whole from the nearest layer. A YAML file holds exactly one YAML document; one with a second is invalid.

Workflow

A workflow composes process calls into one run, and its settings fix what each call receives, never whoever starts it. It has its own params and values, and nodes; each node uses a process and binds the agent that runs it, and agent is required on every node. A process names no agent, so only a workflow runs it. A file value may name brief forms, as a process's may.

It has one of two shapes. One or more processes over the same inputs, run at once, then one process given their results: code_review, adr_review. Or one call, with no input of its own: it takes its process's params and is that call's one run, as implement_codex binds implement to codex-sol-61 and implement_opus binds it to claude-opus. Those are today's limits, not what a workflow is.

A layer rebinds a node: it gives the whole fan_out list, or sets join.agent or call.agent alone. A workflow whose node binds a blocked or broken agent is refused until a layer rebinds it.

Process

A process is the work, and names no agent. It holds the instruction, caller params, input values, the revision input HEAD must be at, whether a fresh call needs a clean worktree, and its own limits: workspace access (read-only unless it says read-write) and scope (candidate or repository), allowed, required and denied permissions, timeout, attempts, cost cap and staleness limits, with under stale.recover how many times a call may resume a stale turn and with what instruction. It speaks in permissions, never in runtime primitives. Limits narrow from the service to the process to the caller's --timeout and --max-cost.

Its session is fresh-only unless it says resumable; a process whose verification repairs, or that may resume a stale turn, must be resumable. It works in the caller's worktree; Agister makes no checkout and runs no setup. A process with a verification, such as implement, is still a process.

A process may extend one base, extends: process:<base>. The base extends nothing and is not work: no node may bind it. Its layers come first, then the extending process's over it; maps merge by key, lists and scalars replace whole, and name and extends are never taken from the base. A partial may not set extends. Home's six reviews, the five code reviews and the ADR review, extend its review base.

The base is of the process's own layer. The layer whose file holds the whole process and names the base defines the base too: its file of the base and the extending file together set every field a process requires. A base only home has, or a repository's partial of it that leaves a required field to home's file, is no base for a process the repository defines: check reports the process and its run is refused. Partials that do not set extends, over a process home defines or over its base, still compose.

What a process names

  • base: the one process it extends, if any.
  • output schema: the JSON Schema its output must match.
  • verification: command, timeout, max attempts, failure instruction; or held inline in the process. It runs in the call's worktree.
  • prompts: plain text, named by one required prompt and a guidance list; a missing name refuses the call.
  • skills: each one SKILL.md.
  • brief forms: briefs/<name>.yaml, named by a file input's form: [goal, step]. Each holds its parts in order, each a heading, required or not, with the exact text it must read (Open: None.) or a file it refers to, and the template a caller copies. A call whose text has none of its forms is refused before it starts, naming each wrong part. Agister checks the structure, never the meaning. A workflow's file value may name them too; the diagram draws them under the process.

Agent

An agent is a runtime profile: runtime, model, model family, effort and command. It carries no task, no permissions, no limits and no session. It names a runtime mapping and its own skills; a node's call gets its process's skills, then its agent's, each once.

Runtime mapping

A runtime mapping covers one adapter (claude-code, codex, pi or opencode): the efforts it accepts and each restriction primitive, a tool or sandbox mode, with the permissions it grants.

Service

The hard limits (max timeout, attempts, cost, verify attempts) and the permission vocabulary, including which permissions write and which reach Agister's state; those are never granted. No document names the service; it applies to every run. A process uses only its permissions, within its limits; a runtime mapping grants only its permissions.

Where permissions meet primitives

The process's effective permissions meet the bound agent's runtime mapping to make the enforcement plan. For select: one, the narrowest safe primitive covering tools.require is selected; grants beyond the best-effort tools.allow ceiling warn. For select: any, fitting safe tools are granted. State-reaching grants remain forbidden. An allowed permission that no primitive provides is withheld, and the call is refused if the process requires it. check makes the plan for every node of every workflow: a binding that would be refused is a problem of that workflow, naming the node, and one that withholds an allowed permission is listed as withheld. Extra grants warn per binding and are recorded beside declared and granted permissions; run outcomes and printed results carry the warning. Unverified versions warn; probes are observability (ADR-036).

Blocks

Two more documents, not in the diagram: layer.yaml names additional prompt folders in a repository or project; blocks, repo only: the agents, processes, workflows or runtime mappings this repo refuses, with reasons; a workflow that binds a blocked agent is refused until a layer rebinds it. A project holds no blocks. Guidance a node must follow belongs in its prompt or guidance, never a pointer in AGENTS.md or a skill. There is no workspace document: workspace.yaml is obsolete, and check warns about it.
