Agister · settings

Agister's settings architecture

Settings define the work; runs and calls are what executed it. Agister reads settings from up to three layers, composes each document field by field, and resolves a request into definitions core can run, or into a refusal that names the chain at fault. Facts and sources are in notes.md; the decisions are ADR-001 to ADR-012.

Three axes

Each thing has one name, on one axis. A definition is declared, resolved and planned; it never runs. An execution starts and ends; it is never declared.

Definitions, in settings:

  • workflow: work defined by inputs, an output contract and children, each a step or a workflow
  • step: a process bound to an agent, the one leaf
  • process: what a step does
  • agent: who does it, on which runtime
  • runtime mapping: grants and options
  • binding, condition: data flow and decisions

Executions, in records; an execution names the definition it executes:

  • run: executes a workflow
  • call: executes a step
  • iteration: one execution of a repetition's body
  • turn: one exchange of a call with its runtime
  • session: the conversation a call held

Machinery, in code:

  • runtime: a program Agister drives through its wrapper
  • runtime facts: what a runtime can do
  • program: an operating-system process
  • hold: a call's claim on the worktree
  • supervisor: runs every program

ADR-012, terms.

What a workflow names

Documents name each other by kind and name, fixed in settings, so they resolve without a run. A workflow composes steps and other workflows by sequence, parallel, branch or bounded repetition. A step binds a process to an agent; nothing but a step chooses an agent. Bash is a runtime like any other: its agent names only the runtime, and its prompt is a script.

Where settings live

Each kind has its folder in a layer, and a document is the file named after it. Nothing but kind and name joins files across layers.

From files to definitions

Resolve is the gate before a run: what resolves may be run, what does not never reaches core and leaves no run. A problem in a document refuses only what depends on it; a refusal names the chain to the document at fault.
