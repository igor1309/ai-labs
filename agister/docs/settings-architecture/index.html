Agister · Settings

Agister's settings architecture

Agister's settings are documents that name each other by name. A workflow names processes. A process names its agent, policy, output schema, verification, prompts and skills. An agent names its runtime mapping and its skills. Under all of them lies the service: the permission vocabulary policies and runtime mappings may use, and the hard limits no policy may exceed.

Two kinds can be run, workflows and processes, both the same way: agister run <name>. The other documents are never run; a run uses them.

Every document can come from the repo's .agister or from home; the repo's replaces home's of the same kind and name.

Workflow

A workflow composes process calls into one run, and its settings fix what each call receives, never whoever starts it. It has its own params and values. Its only shape today is fan-out then join: one or more processes over the same inputs, run at once, then one process given their results.

Process

A process is a named agent call. It holds the instruction, caller params, input values, the checkout input, its own setup, required permissions and limit overrides. Everything else it names.

What a process names

Its agent, and its supporting documents:

  • policy: execution defaults: timeout, attempts, cost cap, allowed and denied permissions, workspace access (read-only or read-write) and scope (candidate or repository), staleness limits. It speaks in permissions, never in runtime primitives.
  • output schema: the JSON Schema its output must match.
  • verification: command, timeout, max attempts, failure instruction; or held inline in the process.
  • prompts: plain text, which may be optional.
  • skills: each one SKILL.md.

Agent

An agent is a runtime profile: model, model family, effort, session mode (fresh-only or resumable). It carries no task and no permissions. It names a runtime mapping and its own skills.

Runtime mapping

A runtime mapping covers one adapter (claude-code, codex, pi or opencode): the efforts it accepts and each restriction primitive, a tool or sandbox mode, with the permissions it grants, verified against runtime versions.

Service

One document under all the others: the hard limits (max timeout, attempts, cost, verify attempts) and the permission vocabulary every policy and runtime mapping must use, including which permissions write and which reach Agister's state; those are never granted.

Workspace and blocks

Two singletons stand apart from the graph: the workspace, the default checkout setup for processes that check out a revision and declare none, and blocks, repo only: the agents, processes, workflows or runtime mappings this repo refuses, with reasons.

Where permissions meet primitives

The effective permissions meet the agent's runtime mapping to make the enforcement plan. A primitive is granted only if everything it grants is allowed. An allowed permission that no primitive provides is withheld, and the call is refused if the process requires it.
