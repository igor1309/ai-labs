Agister's settings architecture

Agister's settings are documents that name each other by name. A workflow names processes. A process names its agent, policy, output schema, verification, prompts and skills. An agent names its runtime mapping and its skills. Over all of them sits the service: the permission vocabulary policies and runtime mappings may use, and the hard limits no policy may exceed.

Every document can come from the repo's .agister or from home; the repo's replaces home's of the same kind and name.

Workflow and process

A workflow is a set of process calls: fan-out nodes, each a call of a process over the same resolved inputs, then one join node, a call of a process given the fan-out results. It has its own params and values. A process is a named agent call. It holds the instruction, caller params, input values, the checkout input, its own setup, required permissions and limit overrides. Everything else it names: its agent, its policy, the schema its JSON output must match, its verification (or holds it inline: command, timeout, max attempts, failure instruction), its prompts, which may be optional, and its skills. A prompt is plain text; a skill is one SKILL.md.

Agent and runtime mapping

An agent is a runtime profile: model, model family, effort, session mode (fresh-only or resumable) and the skills it names. It carries no task and no permissions. It names a runtime mapping, which covers one adapter (claude-code, codex, pi or opencode): the efforts it accepts and each restriction primitive, a tool or sandbox mode, with the permissions it grants, verified against runtime versions.

Policy and service

A policy holds execution defaults: timeout, attempts, cost cap, allowed and denied permissions, workspace access (read-only or read-write) and scope (candidate or repository), staleness limits. It speaks in permissions, never in runtime primitives. The service is one document: the hard limits (max timeout, attempts, cost, verify attempts) and the permission vocabulary every policy and runtime mapping must use, including which permissions write and which reach Agister's state; those are never granted.

Apart from the graph stand two singletons: the workspace, the default checkout setup for processes that check out a revision and declare none, and blocks, repo only: the agents, processes, workflows or runtime mappings this repo refuses, with reasons.

How limits narrow

service ⊇ policy ⊇ process ⊇ caller

Each may only narrow what the one before allows. Widening is rejected, never clamped. Denied always wins over allowed.

Where permissions meet primitives

The effective permissions meet the agent's runtime mapping to make the enforcement plan. A primitive is granted only if everything it grants is allowed. An allowed permission that no primitive provides is withheld, and the call is refused if the process requires it.
