Agister · Settings

Agister's settings architecture

Agister's settings are documents that name each other by name. In agister run <name> the name picks one workflow or one process; nothing else is run. A workflow names processes. A process names its agent, output schema, verification, prompts, skills and policy, and a file input may name the brief forms its text must have. An agent names its runtime mapping and its own skills. The service is never picked: it has no name, and it applies to every run.

A box holds the document's own fields; an arrow is a document it names. Every document can come from the repo's .agister or from home; the repo's replaces home's of the same kind and name.

Workflow

A workflow composes process calls into one run, and its settings fix what each call receives, never whoever starts it. It has its own params and values, and nodes, each naming a process. A file value may name brief forms, as a process's may.

Its only shape today: one or more processes over the same inputs, run at once, then one process given their results. That is today's limit, not what a workflow is. Examples: code_review, adr_review.

Process

A process is a named agent call. It holds the instruction, caller params, input values, the revision input HEAD must be at, whether a fresh call needs a clean worktree, required permissions and limit overrides. It works in the caller's worktree; Agister makes no checkout and runs no setup. A process with a verification, such as implement, is still a process.

What a process names

Its agent, and:

  • output schema: the JSON Schema its output must match.
  • verification: command, timeout, max attempts, failure instruction; or held inline in the process. It runs in the call's worktree.
  • prompts: plain text, which may be optional.
  • skills: each one SKILL.md.
  • brief forms: briefs/<name>.yaml, named by a file input's form: [goal, step]. Each holds its parts in order, each a heading, required or not, with the exact text it must read (Open: None.) or a file it refers to, and the template a caller copies. A call whose text has none of its forms is refused before it starts, naming each wrong part. Agister checks the structure, never the meaning. Not drawn above.
  • policy: execution defaults: timeout, attempts, cost cap, allowed and denied permissions, workspace access (read-only or read-write) and scope (candidate or repository), staleness limits, and under stale.recover how many times a call may resume a stale turn and with what instruction. A process may only lower that number. It speaks in permissions, never in runtime primitives.

Agent

An agent is a runtime profile: model, model family, effort, session mode (fresh-only or resumable). It carries no task and no permissions. It names a runtime mapping and its own skills, separate from the process's.

Runtime mapping

A runtime mapping covers one adapter (claude-code, codex, pi or opencode): the efforts it accepts and each restriction primitive, a tool or sandbox mode, with the permissions it grants.

Service

The hard limits (max timeout, attempts, cost, verify attempts) and the permission vocabulary, including which permissions write and which reach Agister's state; those are never granted. No document names the service; it applies to every run. A policy uses only its permissions, within its limits; a runtime mapping grants only its permissions.

Where permissions meet primitives

The effective permissions meet the agent's runtime mapping to make the enforcement plan. A primitive is granted only if everything it grants is allowed. An allowed permission that no primitive provides is withheld, and the call is refused if the process requires it.

Blocks

One more document, not in the diagram: blocks, repo only: the agents, processes, workflows or runtime mappings this repo refuses, with reasons. There is no workspace document: workspace.yaml is obsolete, and check warns about it.
