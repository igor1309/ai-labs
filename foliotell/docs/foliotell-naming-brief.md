# Document-to-Speech App Naming Brief

## Product Scope

### v0.0.1 target field

A document-to-speech app that reads local Markdown files aloud.

Core product behavior:

- low-friction access to files in a folder;
- document-oriented interface rather than repeated use of the standard file picker;
- Markdown support, with plain-text reading acceptable initially;
- selectable playback speed:
  - 1×
  - 1.25×
  - 1.5×
  - 1.75×
  - 2×.

### Reasonable adjacent category

Broader text-to-speech readers that may later support:

- plain text;
- additional document formats;
- pasted text;
- other local files.

### Out of scope for collision screening

General listening-productivity products such as:

- read-later apps;
- audiobook apps;
- podcast apps;
- generic audio-content platforms.

These are too broad to define the target naming field.

## Naming Objective

The name should:

- fit a document-to-speech product;
- remain usable if the app expands beyond Markdown;
- work as a public brand;
- survive spoken reference;
- have clear spelling and pronunciation;
- avoid close collisions in the target field and adjacent category.

## Technical and Brand Surface

The name should be checked across:

- Apple App Store;
- iOS and macOS product naming;
- domains;
- GitHub organization and repository naming;
- social handles.

Domain or handle availability is useful but not a primary ranking criterion at this stage.

## Semantic Direction

Use both of these naming modes:

### Balanced compounds

Combine a content/document concept with a speech/audio concept.

Examples of useful root families:

**Speech / audio**

- speak
- voice
- vocal
- narrate
- say
- recite
- audio
- vox
- tone
- echo
- cast
- listen

**Content / document**

- text
- file
- document
- doc
- note
- page
- mark
- script
- prose
- draft
- paper
- folder
- library
- shelf
- fold
- stream

### Abstract or coined names

Invented or indirect names are acceptable when they have:

- strong phonetic clarity;
- simple spelling;
- good spoken referenceability;
- enough distinction to function as a brand;
- a clear product descriptor or subtitle.

## Functional Explicitness

Use a tiered standard:

1. Prefer names that suggest spoken content immediately.
2. Accept names whose meaning becomes clear with an App Store subtitle.
3. Use fully abstract names only when they are unusually strong.

The name should avoid locking the product to Markdown unless format specificity is intentionally desirable.

## Tone

Target tone:

- practical;
- clear;
- modern;
- restrained;
- distinctive enough to function as a brand.

The name may combine utility clarity with a more original brand layer.

Avoid names that feel:

- childish;
- overly soft;
- corporate;
- technical for its own sake;
- generic enough to disappear in search.

## Name Shape

Acceptable structures:

- 2–3 syllable names;
- compact compounds;
- coined words;
- blended roots.

One-syllable names are optional rather than preferred.

## Pronunciation and Spelling

Clarity receives high priority.

Prefer:

- one obvious pronunciation;
- one likely spelling after hearing the name;
- easy spoken reference;
- clean App Store label presentation.

Minor ambiguity is acceptable only when the name is otherwise unusually strong.

There is no broad fallback for difficult pronunciation or spelling.

## Target Languages and Markets

Primary screening scope:

- English;
- major European languages.

Check for:

- strong negative meanings;
- embarrassing everyday phrases;
- severe pronunciation problems;
- misleading category associations.

Neutral cross-language meanings are documentation costs rather than blockers.

## Availability Standard

Availability is a risk filter, not the primary ranking axis.

The goal is meaningful availability inside the target field rather than global uniqueness.

### Hard blockers

Reject a name when there is:

- a same or highly similar name in document-to-speech apps;
- a same or highly similar name in broader text-to-speech readers;
- an active trademark-heavy company in either category;
- strong negative meaning in a target language or market;
- severe pronunciation or spelling ambiguity;
- a direct conflict on the intended technical surface;
- dominant search results from the target field or adjacent category;
- a same or highly similar name associated with malware, scams, sanctions, fraud tracking, or regulatory enforcement.

### Soft concerns

Keep a candidate when collisions are limited to:

- unrelated historical software;
- unrelated SaaS products;
- small GitHub repositories;
- personal handles;
- ordinary grammatical forms;
- unrelated companies;
- broad word-root usage;
- obscure or inactive projects;
- non-primary package registries;
- neutral cross-language overlays.

### Ignore for now

Do not over-weight:

- perfect global uniqueness;
- pristine domain availability;
- every package registry;
- unrelated consumer apps;
- broad trademark paranoia;
- scattered handle usage;
- harmless language coincidences.

## Scoring Model

| Criterion | Weight |
|---|---:|
| Product fit | 35% |
| Spoken usability | 25% |
| Tone fit | 15% |
| Memorability | 15% |
| Availability risk | 10% |

## Availability Risk Scale

| Risk | Meaning |
|---|---|
| Low | No visible target-field collision; unrelated uses only |
| Medium | Visible use outside the target field |
| High | Close adjacent product or dominant adjacent-category search result |
| Blocked | Same or highly similar name in the target field |

## Current Candidate Findings

### Rejected

#### Speakdown

Rejected because “speak down to” has a strong established English meaning: speaking condescendingly to someone.

#### Voxmark

Rejected because the name is already taken.

#### ShelfCast

Rejected because an active software product already uses the same name.

### Weakened

#### NarrateMD

Clear function, but tightly coupled to Markdown and therefore restrictive if the product expands to other file types.

#### Readmark / Readfold / Readflow / Readcast

These names under-signal speech or audio.

#### ShelfVoice

Semantically relevant, but awkward to say.

## Practical Naming Principle

> Prefer a name that suggests spoken documents, remains usable beyond Markdown, is easy to say and spell, and avoids close collisions in document-to-speech and broader text-to-speech products.
