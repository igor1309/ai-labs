# AGENTS (audelin)

Issues are in the Multica project `Audelin`, in the `ai-labs` workspace (parent LAB-400).

- The component diagram is `docs/live-text.drawio`, generated by `scripts/component-diagram.py`
  from `macos/Package.swift` and `macos/App/Package.swift`. Any step that adds a target or changes a dependency reruns it in
  the same commit; a new target needs its lane and line in the script's `TARGETS`, and the
  script stops until it has one.
- Tests do file and process work directly; they do not hop it to a queue. Cleanup is awaited
  with `withCleanup { } cleanup:`, children run through `exitStatus(of:)`, and audio files are
  read with `audioFile(_:)`. Core Audio listener callbacks stay on Core Audio's threads.
- A change meant to make the text path faster is judged by `macos/Benchmarks` (its README):
  median instructions per word against the saved `base`, not by unit or count tests.

- The app and rehearsal compose machines in `macos/App/Sources/Composer`; components stay in
  `macos/Sources`. Build and test both packages from their directories with
  `swift build --build-tests`, then run the tests through `scripts/swift-test-bounded.sh <seconds>`,
  never bare `swift test`: the runner kills a run past its time or memory cap, where a runaway
  test would otherwise exhaust the Mac. `scripts/gate-step.sh` gates both and bundles.

## Design

- The whole Audelin design is one file, `docs/design/visual-language.pen`:
  the Glass Ledger tokens, every component and every screen. Draw new
  screens and states in it; do not start another `.pen` for a feature, not
  even for drafts.
- Its variables are the only token source. Build from its components; a
  new part goes on a components board in that file. `docs/design/tokens.json`
  is a snapshot of those variables and changes with them (steps in
  `docs/design/README.md`).
- Each feature keeps a brief, a Markdown file beside it in `docs/design/`,
  and a row in the README's frame index saying where its frames sit.
- `docs/research/gallery/` holds research boards of other apps, not design.

## Real-audio tests

- Four test files use the Mac's audio hardware through `coreaudiod`: the call-audio probe, the
  Core Audio binding, the microphone binding and the end-to-end recording test. CI skips them
  (`GITHUB_ACTIONS=1`); locally they run with every `swift test`.
- When one fails, do not rerun it to diagnose. Each run opens real audio connections, and a
  failed or hung run can leave them behind; repeated runs grew `coreaudiod` to about 50 GB and
  froze the Mac until a hard reboot.
- On a failure, check `coreaudiod` first: its memory (`ps -Ao rss,command | grep coreaudiod`)
  and its connections from dead processes (`pmset -g assertions`). If it holds either, stop
  every audio run, tell the owner it needs restarting, and gate with `GITHUB_ACTIONS=1` until
  it is.
- To verify these tests, run each file once, on its own, and check `coreaudiod`'s memory after
  each. Stop at the first sign it grows.
