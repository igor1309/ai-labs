# «Вжух» Сбера — техническая архитектура BLE-оплаты на iOS

> **Статус сведений:** публично описанные механизмы, патентный вариант и инженерная реконструкция. Патентные примеры не гарантируют совпадения с рабочим протоколом терминалов Сбера.

## 1. Назначение и компоненты

«Вжух» обеспечивает бесконтактную оплату через Bluetooth Low Energy (BLE): iPhone взаимодействует с совместимым POS-терминалом, а платёж обрабатывается банковской инфраструктурой.

| Компонент | Роль |
|---|---|
| iOS-приложение | Обнаружение POS, выбор терминала, подготовка и передача платёжных данных |
| POS-терминал | BLE advertising/GATT, получение данных и передача операции на сервер |
| Платёжный backend | Проверка реквизитов, авторизация и проведение платежа |
| Сервис токенов | Предварительная выдача краткоживущих/одноразовых платёжных реквизитов для офлайн-сценария |

## 2. Последовательность обмена

```text
 iPhone (BLE Central)          POS (BLE Peripheral)          Backend
         |                            |                         |
         |<--- BLE advertising -------|                         |
         |     service / данные POS  |                         |
         |-- выбор POS по RSSI ------>|                         |
         |-- GATT: фрагменты JWE ---->|                         |
         |<-- подтверждение частей ---|                         |
         |                            |--- платёжные данные --->|
         |                            |<-- результат операции --|
```

Это **концептуальная схема**: конкретный порядок и поля production-обмена публично не подтверждены.

### 2.1. Обнаружение и выбор терминала

1. POS публикует BLE advertising с идентификатором сервиса и данными сессии; состав полей зависит от реализации.
2. Приложение сканирует совместимые устройства через `CBCentralManager`.
3. Для каждого кандидата собирает RSSI, сглаживает измерения и выбирает терминал по скорректированному сигналу и правилам допуска.
4. При необходимости учитываются движение телефона и профиль модели терминала.

Пример сглаживания EMA:

```text
ema[t] = α * rssi[t] + (1 - α) * ema[t-1]
```

В патентном описании приводится пример `α = 0.3`, интервал измерений `0.1 с` и диапазон RSSI `−100…−20 dBm`. Также рассматривается фильтр Калмана. Это **примеры параметров**, а не подтверждённые настройки действующего приложения.

### 2.2. Защищённый обмен

В опубликованном патентном варианте:

1. Терминал формирует сессионную пару асимметричных ключей и предоставляет публичный ключ.
2. Приложение подготавливает платёжный токен и шифрует сообщение для получателя в формате JWE.
3. Шифротекст делится на BLE-фрагменты (в описанном примере — по 160 байт).
4. Фрагменты передаются через GATT; предусмотрена передача индекса ожидаемой части.
5. Терминал собирает сообщение, расшифровывает его и передаёт данные в платёжную инфраструктуру.

Иллюстративный формат части из патентного описания:

```text
<индекс>@<фрагмент>
```

Реальные UUID сервиса и характеристик, порядок сообщений, согласование MTU и механизмы защиты от повторной передачи требуют спецификации Сбера.

### 2.3. Оплата при отсутствии интернета на iPhone

Платёжные реквизиты могут предварительно загружаться в приложение. Во время покупки телефон передаёт их терминалу по BLE; терминал использует своё сетевое соединение для авторизации. Сроки действия, количество токенов и правила пополнения запаса для iPhone публично не установлены. Опубликованный пример **10 токенов на неделю** относится к умному кольцу SberDevices.

## 3. JWK и JWE

### JWK — JSON Web Key

**JWK** — стандартное JSON-представление криптографического ключа (RFC 7517). Позволяет передавать параметры публичного ключа вместе с указанием его типа и назначения.

Пример структуры публичного EC-ключа (значения сокращены и условны):

```json
{
  "kty": "EC",
  "crv": "P-256",
  "x": "base64url-x-coordinate",
  "y": "base64url-y-coordinate",
  "kid": "session-key-01"
}
```

- `kty` — тип ключа;
- `crv` — эллиптическая кривая;
- `x`, `y` — координаты публичной точки в кодировке base64url;
- `kid` — идентификатор ключа.

**JWK — формат представления ключа**, а не алгоритм шифрования. Пример показывает возможную структуру; конкретная кривая и поля «Вжух» публично не подтверждены.

### JWE — JSON Web Encryption

**JWE** — стандарт защищённого контейнера для шифрования данных (RFC 7516). Он задаёт представление зашифрованного сообщения, параметры алгоритмов и сведения, необходимые получателю для расшифрования.

Компактная сериализация JWE содержит пять частей:

```text
BASE64URL(header).BASE64URL(encrypted_key).BASE64URL(iv).BASE64URL(ciphertext).BASE64URL(tag)
```

| Поле | Смысл |
|---|---|
| `header` | Алгоритм управления ключом (`alg`) и алгоритм шифрования содержимого (`enc`) |
| `encrypted_key` | Зашифрованный/обёрнутый ключ содержимого; в некоторых режимах пуст |
| `iv` | Вектор инициализации / nonce |
| `ciphertext` | Зашифрованный платёжный payload |
| `tag` | Тег аутентификации для проверки целостности |

Принцип взаимодействия: **JWK предоставляет публичный ключ терминала → приложение использует его в выбранной схеме JWE → терминал расшифровывает сообщение своим закрытым ключом**. Конкретные `alg`/`enc`, способ доставки JWK и валидация его подлинности — отдельные параметры протокола. Публичный ключ должен быть привязан к доверенному терминалу/сессии, иначе возникает риск подмены получателя.

## 4. Реализация на iOS

| Задача | API / компонент | Примечание |
|---|---|---|
| BLE discovery | `CBCentralManager.scanForPeripherals` | Фильтрация по известным service UUID |
| RSSI | `centralManager(_:didDiscover:advertisementData:rssi:)` | Накопление измерений по терминалам |
| Выбор POS | Swift: EMA/Калман, состояние сессии | Устойчивость к соседним терминалам |
| Соединение и GATT | `CBPeripheral`, `CBCharacteristic` | Чтение/запись/уведомления согласно спецификации |
| Движение | `CoreMotion` | Дополнительный сигнал для ранжирования |
| Ключи и криптография | `Security`, `CryptoKit` и реализация JOSE | Нужна совместимость с выбранными алгоритмами JWE |
| Хранение секретов | Keychain | Политики доступа и жизненный цикл токенов |
| Подтверждение действия | `LocalAuthentication` | UX и локальная авторизация при необходимости |

**Ограничение iOS:** фоновые BLE-сканирования имеют особые правила доставки событий и могут объединять повторные advertising-события. Для прототипа с плотным сбором RSSI целесообразен активный экран приложения.

## 5. Что нужно для совместимости с терминалами Сбера

| Требуется | Публичный статус |
|---|---|
| Production service/characteristic UUID | Не установлен |
| Формат advertising и GATT-сообщений | Полная спецификация не опубликована |
| Криптографические алгоритмы и доверенная привязка ключей | Не установлены |
| Выдача и обновление платёжных токенов | Требуется банковская интеграция |
| Идентификация приложения/партнёра и сертификация | Требуется согласование со Сбером |
| Ошибки, тайм-ауты, повторы, защита от replay | Требуется спецификация |

**Практическое разделение:** собственный прототип позволяет воспроизвести discovery, выбор POS и защищённую передачу тестового payload. Реальная оплата на терминалах Сбера требует совместимого протокола и партнёрского доступа к платёжной инфраструктуре.
