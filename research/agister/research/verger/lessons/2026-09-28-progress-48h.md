# Why 48 hours of the loop produced little progress (28.09.2026)

Window: 26.09 07:20 → 28.09 07:20 MSK. Source: `dev/report.sh --since "48 hours ago"`, tracker
commit history.

**Numbers.** 245 steps accepted (5.1/h); Go +4 797 production, +18 082 test lines (≈20 prod,
≈74 test per step). Of 246 done rows: 113 M7, 90 DEV, 43 other; 138 were follow-up rows
(`-r`, `-fix`, `-flake`). 329 judge commits. Queue still 49 rows. Six full-tier runs FAILed and
none was re-run. No milestone closed.

Busy, not moving: most of the output was follow-ups and loop tooling, and no milestone closed.

## 1. Reviews generate work as fast as it is done

Every accepted step gets a Codex review, which usually yields 1–2 rows; chains reach depth 3
(`DEV-conflict.1-r2-r1`).

- **A. Only P1 findings become rows; P2/P3 go to a milestone-end list.** Pro: roughly halves new
  rows. Con: real P2 bugs wait; the end list grows.
- **B. Review per batch (e.g. 10 steps of one module).** Pro: one review sees the combined change.
  Con: findings harder to attribute; fixes later.
- **C. Cap chains at depth 1.** Pro: kills `-r2-r1` churn. Con: a real fault in a fix may pass.

**Lean: A** — most rows are P2 edge cases in test or tooling code.

## 2. A third of the output is loop tooling

90 of 246 steps were DEV, mostly follow-ups of other DEV steps.

- **A. Freeze DEV except blockers.** Pro: both dev lanes go to M7. Con: rough edges stay; more
  orchestrator judgement.
- **B. Cap DEV at one lane.** Pro: product gets 7 of 8 lanes. Con: 12 DEV rows drain slowly;
  reviews still add rows.
- **C. No reviews for DEV steps; the devsuite is the only check.** Pro: about 40% less review churn.
  Con: `accept.sh` bugs reach the loop unreviewed.

**Lean: A + C** — the loop already lands 245 steps; polishing it is the churn.

## 3. Session-limit outages

Today two outages took about 5.5 of 8 hours, killing every builder mid-step. 26.09 16:00 →
27.09 04:00 ran 4–8 steps per four-hour block.

- **A. Build with Codex (`codex exec` builders); Claude orchestrates and judges.** Pro: uses paid,
  idle ChatGPT capacity. Con: needs a wrapper and brief; unproven as a builder here.
- **B. Claude builders on Sonnet, Opus for judges.** Pro: about 3–5× more from the same limit.
  Con: weaker on subtle concurrency steps.
- **C. 5 lanes instead of 8.** Pro: no dead builders; steadier. Con: lower peak; budget guessed.

**Lean: A**, with B as the stopgap while A is set up.

## 4. Steps are tiny and heavy on tests

Each step still pays spin-up, gate (204 s), plants (87 s), review and judge.

- **A. 10–12-scenario steps for providers/codex.** Pro: fewer gates and reviews. Con: builders
  stalled at 15.
- **B. Plants only on steps that change production code.** Pro: saves 1–5 min and a lock slot per
  test or docs step. Con: weak tests on test-only steps go uncaught.
- **C. Keep the size rule; land 2–3 steps per gate and review via `--with`.** Pro: overhead shared.
  Con: one failure blocks the stack.

**Lean: B** — XT.4 and XT.5 (test-only) paid full plant cost to prove nothing changed.

## 5. One gate lock for everything

`/tmp/verger-dev.lock` serialises gates, plants and devsuite; a 30 s plants run waited 37 min.

- **A. Separate locks per module or kind.** Pro: dev and plants stop queueing behind codex gates.
  Con: more concurrent load; `-race` runs may flake.
- **B. Two slots for providers/codex.** Pro: halves the worst waits. Con: more HANG/SLOW noise.
- **C. 4 codex lanes plus more dev and doc lanes.** Pro: no code change. Con: fewer codex steps.

**Lean: A** — most waits are cross-kind.

## 6. Integration is never green, so M7 never closes

Six full-tier FAILs (from `c55c611c`) were left unaddressed; X-assembly.1 is still behind wiring
rows. With the provider not assembled end to end, the progress is invisible.

- **A. Run the full integration now; fix before new rows.** Pro: cross-step breakage found while
  small. Con: about 10 min of the lock; lanes pause.
- **B. Critical path first: XD.wire → X-assembly.1 → XP4-compose.1.** Pro: a runnable provider.
  Con: jumps review follow-ups, some real bugs.
- **C. A full FAIL blocks new starts on its module.** Pro: failures stop piling up. Con: one flaky
  test stalls a module.

**Lean: A then B.**

## 7. Spec-first decisions add rows too

21 decisions in 48 h (D-22 to D-42), each adding a docs row and often a code row, several for
untestable windows (D-41, D-42).

- **A. Allow "accept, document only" when a gap is untestable.** Pro: cheap rulings. Con: may
  under-fix a real race.
- **B. One batched `M7-doc` row per day.** Pro: fewer builders and gates for plan text. Con: plan
  lags code by a day.
- **C. Raise only questions that block a step; builders' notes go to a milestone-end list.**
  Pro: far fewer decisions. Con: gaps surface later.

**Lean: C + B.**
