# Quota-Aware Account Selection: Implementation Notes

These notes operationalize the policy in [account-selection-adr.md](./account-selection-adr.md). They do not change the decision recorded in the ADR.

- **Ranking direction:** select the account whose `(min(short_ratio, weekly_ratio), max(short_ratio, weekly_ratio))` pair is lexicographically greatest. Apply the deterministic tie-breaker only when both components are exactly equal.
- **Quota state:** use one snapshot per selection. For each horizon it holds the used fraction, the reset time, the interval duration, and the local time the snapshot was received. Providers report usage as a percentage, not as absolute quota, so derive the used fraction from that percentage. Take the interval duration from the provider where reported (for example, Codex `limit_window_seconds`); otherwise configure it (5 hours and 7 days).
- **Missing horizons:** a provider may report no window for a horizon. Treat it as a fresh interval (ratio `1`) only where the provider documents that an absent window means one has not started; otherwise the snapshot is non-authoritative.
- **Staleness:** a snapshot older than a configured maximum age is non-authoritative. Measure age from the local receipt time, not a provider timestamp. The used fraction is taken as observed; `remaining_time_fraction` is evaluated at selection time.
- **Fractions:** `remaining_fraction = 1 − used_fraction − reserved_fraction`, and `remaining_time_fraction = (reset_time − now) / interval_duration`. Clamp both to `[0, 1]` to absorb provider anomalies such as usage above 100% or a reset time more than one interval away.
- **Reset boundaries:** once `now` reaches a horizon's reset time, including a reset that occurs after the snapshot was taken, the observed usage belongs to the previous interval. Treat that horizon as non-authoritative, refresh the snapshot, and reselect. This also guarantees that every ranked ratio has a positive denominator. Provider reset timestamps can shift by fractions of a second between reads; detect a reset by comparing `now` with the snapshot's reset time at whole-second resolution, not by comparing reset times across snapshots.
- **Eligibility:** an account is eligible only when its snapshot is authoritative on every horizon and `remaining_fraction` covers the configured per-session cost estimate on every horizon. If no account is eligible, refresh the snapshots before failing or applying the caller’s retry policy.
- **Recomputation:** compute the ranking at every selection; do not cache it. Ratios depend on the current time, so accounts with different reset times can change order without any consumption or reset.
- **Reservations:** select and reserve atomically, so concurrent selections cannot all act on the same unconsumed quota. A reservation holds the per-session cost estimate on every horizon of the selected account, together with the used fraction reported when it was made. Reported usage lags actual usage; apply later increases in reported usage to outstanding reservations, oldest first, until each reaches zero, so consumption is neither ignored nor double-counted. On a reset, rebase outstanding reservations onto the new interval's reported usage. Expire reservations after a configured TTL so abandoned sessions do not hold quota indefinitely. After a rejected reservation, refresh the snapshots and retry according to the caller’s retry policy.
- **Persistence:** persist outstanding reservations with their baselines and expiry, so a restart does not forget in-flight consumption.
- **Arithmetic:** represent inputs as integers: used fractions in basis points and times in whole seconds. Compare ratios by cross-multiplication (`a/b > c/d` ⟺ `a·d > c·b` for positive `b` and `d`) rather than division, so exact ties stay exact. Comparing the short and weekly ratios multiplies terms from different horizons; at these units the products stay below about `4·10^15` and fit in 64-bit integers, whereas finer units need wider integers. Provider percentages are coarse (Codex reports whole percents), so exact ties are routine rather than exceptional.
- **Clocks:** compare reset times with the current wall-clock time in UTC. Use a monotonic clock for snapshot age and reservation TTLs.
- **Tie-breaker:** among tied accounts, choose the one with the highest stable hash (for example, SHA-256) of `(session_id, account_id)`. Rendezvous hashing is deterministic, spreads tied selections across accounts, needs no shared state, and removing an account from the tie leaves the others’ relative order unchanged. Do not use a per-process randomized hash.
- **Observability:** record the selected account, both ratios, eligibility exclusions, snapshot age, outstanding reservations, and the tie-break outcome so pacing decisions can be diagnosed without exposing credentials.
- **Testing:** cover exact primary ties resolved by the secondary value; full ties resolved by the tie-breaker, with the same result across runs; a change in ranking caused only by elapsed time; a reset instant and a reset after the snapshot; near-reset ratio growth; stale snapshots; missing horizons; reservation accounting without omission or double counting, including expiry; concurrent selections that must not overcommit; and the no-eligible-account path.
