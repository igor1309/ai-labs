## Вход

```text
GOOGLE_SHEETS_URL: {{GOOGLE_SHEETS_URL}}
DEVELOPER: {{DEVELOPER}}
```

Если `GOOGLE_SHEETS_URL` не указан — запросить ссылку на Google Sheets документ.

Если `DEVELOPER` не указан — запросить, чьи задачи нужно отобрать. Допустимые ответы включают конкретное имя разработчика, `все` или `любой`.

Если в таблице тикетов нет колонки `разработчик` / `developer` / `assignee`, не фильтровать по разработчику и включать все незавершённые задачи.

## Задача

Найти незавершённые задачи из Google Sheets и собрать по ним итоговый Markdown-документ.

Если `DEVELOPER` задан конкретным именем и в таблице есть колонка разработчика — включать только задачи этого разработчика.

Если `DEVELOPER` указан как `все` / `любой` или в таблице нет колонки разработчика — включать все незавершённые задачи.

Статусы могут называться по-разному. Определять незавершённость по смыслу статуса, стадии задачи и близких по смыслу полей вроде `resolution`, `stage`, `этап`, `результат`. Не включать задачи, которые по смыслу явно завершены, закрыты, отменены, отклонены или зарелизены. Если статус неоднозначный — включать задачу и отметить неоднозначность в `Notes`.

## Правила обработки

- Работать с фактически доступными полями и текстом: строгого формата тикета нет.
- Определять смысл колонок по заголовку, содержимому ячеек и соседним полям; порядок колонок не считать значимым.
- Если заголовок колонки пустой или непонятный, но в колонке есть полезные данные, переносить их в `Details` или `Notes` как `Unnamed column N`.
- Не отбрасывать непустые данные из нераспознанных колонок. Переносить их в карточку тикета с исходным названием колонки.
- Важность брать из существующей колонки важности и переносить как есть.
- Feature / фича / сегмент / группа — считать одним и тем же уровнем классификации: `Feature`.
- Статус, важность, название, ссылки, заметки и другие полезные поля переносить без переименования смысла и без нормализации значений, если это не требуется для читаемости итогового Markdown.
- Если название тикета отсутствует, но строка содержит кейс, шаги, ОР/ФР, комментарий, ссылку или другую содержательную информацию — не исключать задачу. В поле `Ticket` писать `not specified`, а `Summary` выводить из доступного контекста и помечать `inferred`.
- К полезным деталям тикета относить шаги воспроизведения, ожидаемый результат, фактический результат, комментарии QA/разработчика/аналитика, ссылки на макеты, вложения, логи, скриншоты, документы, API endpoints, тексты ошибок и условия воспроизведения.
- Если у задачи есть ссылка на отдельный tab / лист внутри Google Sheets, открыть его и извлечь дополнительные детали тикета.
- Детали из отдельных листов добавлять в карточку тикета и, при необходимости, кратко отражать в `Notes`.
- Если соседние строки выглядят как продолжение одной задачи, объединять их только при высокой уверенности. Если уверенности нет — оставить отдельными задачами и отметить возможную связь в `Notes`.
- В `Source` указывать лист и номер строки или диапазон строк, если это доступно.
- Не выдумывать отсутствующие данные.
- Если поле отсутствует, писать `not specified`.
- Если значение приходится выводить из контекста, помечать `inferred`.
- Если ссылка на tab недоступна или не содержит полезных деталей, отметить это.

## Итоговый Markdown-документ

Документ должен содержать три раздела.

### 1. Таблица по важности

Показать все найденные незавершённые задачи, отсортированные по убыванию важности.

### 2. Таблица по фичам

Показать те же самые задачи и те же самые колонки, но сгруппировать строки по `Feature`.

Внутри каждой `Feature` сортировать задачи по убыванию важности.

### 3. Список тикетов

Для каждого тикета дать отдельную карточку:

```markdown
### {{Ticket title}}

- Importance:
- Feature:
- Status:
- Source:
- Details source:
- Summary:
- Details:
- Notes:
- Next action:
```

## Общие требования к таблицам

Обе таблицы должны:

- содержать один и тот же набор тикетов;
- использовать один и тот же набор колонок;
- отличаться только сортировкой и группировкой;
- сортировать задачи по убыванию важности: глобально в таблице по важности, локально внутри каждой `Feature` в таблице по фичам.

Рекомендуемый набор колонок для обеих таблиц:

| Importance | Feature | Ticket | Status | Source | Notes | Next action |
|---|---|---|---|---|---|---|

## Ограничения

- Не добавлять явно завершённые тикеты.
- Не менять смысл исходных данных.
- Не превращать задачу в формальную нормализацию таблицы: цель — обзор незавершённых задач, а не очистка исходного документа.
