Reinix Orchestration

A recursive composition over a single primitive — a verifiable task — coordinated by three flow-ignorant agents and an injected adjudication policy.

v0.0.1 2026-04-22 source: reinix-orchestration.md
Initial draft — records ideas and architecture-level concepts. Not exhaustive, not complete.

Simplifying assumptions

Intentional simplifications that scope this draft.

Assumption

Async & failable. All agent calls are async and failable.

Assumption

Stop on failure. Any agent failure stops the flow.

Assumption

Separate workspace. Work is performed in a separate workspace.

Core invariant

One primitive holds the whole flow together.

The flow is a recursive composition over a single primitive: a valid task — a verifiable task, i.e. one containing “done” criteria.

Every entry point to the Orchestrator’s loop — initial input and Remediator output alike — is a valid task. The Orchestrator has no separate “fresh task” vs “fix task” code paths.

Actors

Three agents, all flow-ignorant peers. Each is defined by a typed input/output contract, unaware of each other or of the loop. The Orchestrator coordinates them.

Producer

Sonnet-level · Agent
invalid task
outlist of artifacts

Performs the task and returns artifacts as a grounded claim of completion, carrying evidence against the done criteria and the walked checklist. No judgment — the claim is grounded in the task’s own done criteria.

Reviewer

Opus-level · Agent
intask + work
outstructured verdict

Adversarial and broad: structure, clarity, quality, and completeness beyond the stated criteria. Reviewer assesses the work; Producer grounds the claim. Review schema is reused from the existing review skill.

Remediator

Opus-level · Agent
intask + work + verdict + history
outvalid task (fix plan)

Produces a valid task — a fix plan conforming to the same verifiable-task contract the Orchestrator accepts at entry. Knows nothing about the flow.

Orchestrator

Runtime · Coordinator
graphtree, never cyclic
scopesequencing + stop-on-failure

Runs within a selected workspace, sequences agent calls, enforces stop-on-failure. Consults ReviewFixPolicy for every routing decision. Workspace lifecycle is intentionally out of scope. Agents never invoke each other or the Orchestrator.

Flow

Five steps. Step 5 re-enters Step 2 with the remediated task.

  1. Orchestrator receives a valid task.
  2. Orchestrator calls Producer. On failure, stop. On success, Producer returns a list of artifacts.
  3. Orchestrator calls Reviewer. On failure, stop. On success, Reviewer returns a structured verdict.
  4. Orchestrator calls ReviewFixPolicy with the verdict and the current session. Policy returns a decision — one of complete-ok, complete-fail, remediate — and the session for the next round.
  5. On remediate, Orchestrator calls Remediator, receives a new valid task, and re-enters step 2.

ReviewFixPolicy

A protocol injected into the Orchestrator. The adjudicator of the flow. Given a verdict and the current session, returns a routing decision and the session for the next round. The Orchestrator is the courier of the session across rounds — it threads it through but does not inspect it.

Owns

Turn budget

Whether the loop can afford another round.

Owns

Routing decision

Where the flow goes next based on verdict severity and session state.

Owns

Session

Opaque object threaded across rounds for cross-round reasoning: no-progress detection, iteration comparison, per-task-class accounting.

Example policy behaviors

Condition Decision
No failures, no warnings complete-ok
F1 failures present, budget exhausted complete-fail
F2-only failures, budget remaining remediate
Same F2 finding recurring across rounds (via session) complete-fail — even with budget remaining

Threshold tuning, severity mapping, per-task-class policies, and convergence detection are all policy concerns and evolve independently of the Orchestrator.

Out of scope for this draft

Acknowledged and intentionally deferred, not forgotten.

Context management

What exactly Producer returns, what Reviewer inspects, how artifacts are framed. A separate concern with its own responsibility; deliberately not mixed into this doc.

Workspace lifecycle

Creation, integration on success, cleanup on stop/exhaustion. Simple, to be specified.

Review verdict schema

Reused from the existing review skill.

Addendum: coding-task specialization

When the task is a coding change, two specializations apply.

Workspace → git worktree
Artifacts → commits
