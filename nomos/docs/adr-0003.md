# ADR-0003: Staging Environment

Status: Proposed
Scope: Nomos deployment topology and release pipeline
Related: ADR-0001 (VPS-first deployment), ADR-0002 (CI/CD deployment via SSH)

---

## 1. Executive Summary

Nomos currently serves production traffic (`/v1/*`) and a stub/test endpoint (`/stub/v1/*`) from a single container on the VPS. This conflates two concerns: there is no way to validate a new release against real vendor APIs before it becomes production. A second Docker Compose stack on the same VPS, fronted by a staging subdomain, provides release validation without additional infrastructure cost.

---

## 2. Context

- The production instance at `nomos.enoa.ai` runs both the live runner (real vendor calls) and the stub runner (fixture responses) in the same process.
- The stub endpoint is a testing convenience (deterministic fixtures), not a staging environment. It cannot validate real vendor integration, streaming, safeguards behavior, or budget enforcement against actual API responses.
- New versions deploy directly to production on tag push (`release-unit.yml` → `deploy-nomos`). A bad release is only caught by the post-deploy smoke test — by which point production is already running the new code.
- The VPS (1 vCPU / 1 GB RAM) has headroom for a second lightweight Nomos container. The Nomos image is ~80 MB and idles at negligible CPU/memory.
- A separate VPS was considered but rejected: doubles cost, doubles operational surface, and the current traffic level does not justify infrastructure redundancy (consistent with ADR-0001's VPS-first rationale).

---

## 3. Decision

Add a staging environment as a second Docker Compose stack on the same VPS, accessible at `staging.nomos.enoa.ai`. A single Caddy instance routes both domains. The CI release pipeline deploys to staging first, runs smoke tests, and only then promotes to production.

The stub endpoint (`/stub/v1/*`) is removed from the production deployment. Stub remains available for local development and e2e tests via `docker-compose.e2e.yml`.

---

## 4. Rules / Invariants

### Infrastructure

- Staging MUST run as a separate Docker Compose project (`nomos-staging`) with its own container name (`nomos-staging`), volume (`nomos-staging-data`), and env file (`.env.staging`).
- Staging MUST listen on an internal port distinct from production (e.g., `8081`).
- Staging MUST use the same vendor API key and base URL as production (validates the real integration path).
- Staging MUST have its own SQLite database (separate volume). Production data MUST NOT leak into staging or vice versa.
- Staging MUST have `NOMOS_STUB_ENABLED=false`. The staging environment validates real vendor calls, not fixtures.
- A single Caddy instance MUST serve both `nomos.enoa.ai` (production) and `staging.nomos.enoa.ai` (staging).
- DNS: `staging.nomos.enoa.ai` MUST have an A-record pointing to the same VPS IP, DNS-only (grey cloud).

### Repository artifacts

- `docker-compose.staging.yml` MUST define the staging stack.
- `.env.staging.example` MUST be committed as a configuration template.
- The production `Caddyfile` on the VPS MUST be updated to route both domains. The repo's `Caddyfile` (local dev) is unchanged.
- `docs/vps-deployment-guide.md` MUST document staging setup.

### Release pipeline

- The `deploy-nomos` job in `release-unit.yml` MUST be split into two sequential jobs: `deploy-nomos-staging` → `deploy-nomos-prod`.
- `deploy-nomos-staging` MUST deploy the new version to the staging stack and run a smoke test (health check + real LLM call via staging domain).
- `deploy-nomos-prod` MUST run only after `deploy-nomos-staging` succeeds.
- Staging smoke test MUST use a dedicated token (`NOMOS_STAGING_SMOKE_TOKEN`) and the staging domain.

### Stub endpoint

- Production `.env` MUST set `NOMOS_STUB_ENABLED=false` (already the case).
- The stub endpoint remains in the application code (controlled by config). No application code changes are required.

---

## 5. Consequences

- Every release is validated on staging before reaching production. A failing smoke test on staging blocks the production deploy.
- Staging smoke tests consume real vendor API tokens (one cheap call per release). This is acceptable and intentional — it validates the real path.
- The VPS runs two Nomos containers instead of one. At idle, the additional resource consumption is negligible. Under simultaneous load, they share the single vCPU — but staging sees near-zero traffic (only CI smoke tests).
- Operators must manage two env files (`.env` and `.env.staging`) and register a staging smoke-test project in the staging database.
- Rollback on staging is trivial: the staging container can be stopped or redeployed independently of production.
- Future extension: staging could serve as a preview environment for PR-based deploys, but that is not in scope for this ADR.

---

## 6. Non-Goals

- Blue-green or zero-downtime deployment within either environment.
- Separate VPS for staging.
- Shared database between staging and production.
- PR-based preview deployments.
- Automated rollback on staging failure (CI simply blocks the production deploy).
- Load testing or performance benchmarking on staging.
- Removing the stub runner from the application code (it remains config-gated for local dev and e2e tests).
