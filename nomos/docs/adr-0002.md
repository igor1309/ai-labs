# ADR-0002: CI/CD Deployment via SSH

Status: Accepted
Scope: Nomos VPS deployment automation
Related: ADR-0001 (VPS-first deployment), release-unit.yml

---

## 1. Executive Summary

Nomos deploys to its VPS automatically when a `nomos_v*` tag is pushed. The existing `release-unit.yml` workflow gains a `deploy` job that SSHs into the VPS, copies source files, rebuilds the Docker image, and restarts the stack. This follows the same pattern used by trend-scout-agent.

---

## 2. Context

- Nomos runs on a single VPS (95.164.53.144) as a Docker Compose stack.
- The initial deployment was performed manually (scp + docker build + docker compose up).
- Manual deploys are error-prone and unrepeatable.
- The trend-scout project on the same VPS already uses CI SSH deploy via `appleboy/ssh-action`.
- A Docker registry (GHCR) was considered but rejected: single deployment target, no multi-node scaling planned, and the image builds in under 10 seconds on the VPS.

---

## 3. Decision

Add a `deploy` job to `release-unit.yml` that triggers only for Nomos releases. The job SSHs into the VPS, syncs source files from the repository, rebuilds the Docker image, restarts the Compose stack, and verifies the health endpoint.

---

## 4. Rules / Invariants

- The `deploy` job MUST run only after `core` (typecheck + tests) passes.
- The `deploy` job MUST be conditional on `needs.verify.outputs.basename == 'nomos'`.
- Deployment MUST use `appleboy/ssh-action` with secrets `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`.
- The deploy script MUST:
  1. Stop the running stack (`docker compose down`).
  2. Copy updated source files (Dockerfile, package.json, package-lock.json, src/).
  3. Rebuild the Docker image (`docker build -t nomos:latest .`).
  4. Start the stack (`docker compose up -d`).
  5. Wait for healthy status and verify the health endpoint returns `{"status":"ok"}`.
- The deploy script MUST NOT touch `.env`, `Caddyfile`, or `data/` — those are operator-managed on the VPS.
- GitHub secrets `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY` MUST be configured in the ai-labs repository.
- The `github-release` job MUST depend on `deploy` (not just `core`) for Nomos releases, so a failed deploy blocks the GitHub Release.

---

## 5. Consequences

- Every Nomos tag push results in an automatic VPS deployment.
- No manual SSH or scp required for routine releases.
- Deploy failures are caught by CI and reported via Telegram.
- The VPS needs a clone or checkout of the repo for source access. Alternative: CI can scp files directly (simpler, no git on VPS for this purpose).
- Same VPS secrets are reusable if other projects deploy to the same host.

---

## 6. Non-Goals

- Docker registry (GHCR/Docker Hub) image publishing.
- Blue-green or rolling deployment.
- Multi-VPS or multi-region deployment.
- Database migration automation (SQLite schema changes are handled by the application on startup).
- Automated rollback on deploy failure (manual rollback per ops runbook).
