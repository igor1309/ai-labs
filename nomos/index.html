Nomos

A unified LLM proxy that gives projects one controlled path to model providers.

Nomos sits between internal products and external AI vendors. It owns project identity, budget limits, token usage logging, provider routing, and basic prompt-injection safeguards. Projects integrate once; policy stays centralized.

OpenAI-compatible /v1/chat/completions SQLite usage ledger Docker + Caddy on VPS
Core idea Controls Request flow Stack Docs

Core idea

One service between apps and models.

Nomos is the AI sovereignty layer for the workspace: one Docker service that exposes an OpenAI-compatible API while keeping provider choice, project authorization, spending limits, and usage audit outside individual product code.

Boundary

Provider abstraction

Projects call Nomos instead of binding directly to vendor-specific base URLs, headers, and model routing rules.

Governance

Per-project budgets

Daily and monthly budget checks happen before requests, with token usage recorded after completions and streams.

Safeguards

Prompt hygiene

Requests pass through a lightweight sanitization and suspicious-pattern layer before reaching a live runner.

Controls

Small control plane, explicit behavior.

The service is deliberately narrow: authenticate a project, validate the request, route it, preserve streaming semantics, record usage, and fail closed when policy says no.

Identity

Bearer-token projects

Tokens map to active projects and scopes, separating live provider calls from stubbed local routes.

API

OpenAI-compatible surface

Clients use the familiar chat-completions shape while Nomos owns validation, routing, and runner dispatch.

Audit

Usage reporting

A usage endpoint summarizes project spend signals by period and model from the local SQLite ledger.

Failure mode

Clear local rejections

Oversized JSON, invalid auth, scope mismatches, and budget limits return local errors before provider calls.

Request flow

The path is short and inspectable.

01

Client request

Internal app sends an OpenAI-shaped chat completion request with a project token.

02

Auth + scope

Nomos checks token hash, active project state, and whether the requested route is allowed.

03

Budget gate

Daily and monthly limits are evaluated before model traffic leaves the service.

04

Runner dispatch

Live requests go to the configured vendor endpoint; stub routes use deterministic fixtures.

05

Usage ledger

Completion usage is recorded after non-streaming responses and after streaming finishes.

Stack

Plain runtime pieces.

Nomos is implemented as a compact Node service with persistent local state and Docker-first deployment.
